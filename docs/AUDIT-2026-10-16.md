## 三、未修复的 P1（高）

**体验 / A11y**
1. **触控目标系统性偏小**：390×844 实测多处 **连 WCAG 2.5.8 AA 的 24×24 都不满足** —— 页脚导航项 `24×16`、EntryCard 工具栏 `藏 14×20` / `✓ 11×20` / `传 14×20`、长卷刻度 `8×8`、`← 归急方卷 74×19`、/matrix 条目链接 `214×21`。
2. **设计 token 与 Tailwind 同名不同值**：`--text-lg=22px` 但 `text-lg=18px`；`--space-5=24px` 但 `p-5=20px`；`--text-2xl=36px` 但 `text-2xl=24px`。同页并存两套字号，靠"名字"无法推理。另有一批 token（`--ease-fold`/`--radius-sm`/`--text-display`/`--container-*`）**全站零引用**。
3. **`--color-seal` on `--color-bg-alt` = 4.41:1**（差 0.09 达标）→ 首页/矩阵/海报凡"朱砂字 + bg-alt 底"都略低。
4. **/matrix 深色格内 11px 文字 3.25–4.20:1**（格子底色叠了朱砂透明度）。
5. **/explore 标题层级错乱**：侧栏 h3 排在 h1 之前；50 个条目标题是 `h3 role="button"`（`role` 覆盖标题语义，读屏 H 键导航找不到）。
6. **/matrix 0 格点击无反馈**：点"0 条"格后列表区整个消失，无空态说明。
7. **首页长卷 136 个 Tab 站**，键盘用户须按 136 次 Tab 才能越过。
8. **/my 的 `role="tablist"` 语义不完整**（无 `tabpanel`/`aria-controls`/roving tabindex/方向键）。
9. **Toast 的 live region 与内容同时挂载**（静息态 `aria-live` 命中 0），NVDA/JAWS 常漏播。
10. **/explore 侧栏章节名在 ≥768px 截断 8 处**（最多缺 106px），兜底只有 hover `title` → **触屏 iPad 完全读不到完整章名**。

12. **暗色模式半失效**：`prefers-color-scheme: dark` 只改了 `html`，`body` 仍米色；`.force-light` 是死代码。

## 六、修复过程中自己引入并已修掉的两个回归（留作教训）

1. **修软 404 时打断了路由预取**：给 `[scenario]` 加 `dynamicParams = false`，但 `generateStaticParams` 返回的是 `encodeURIComponent(slug)`。Next 会**先解码 URL 段再匹配 params**，两者永远不一致 → 12 个场景页的 `?_rsc=` 预取请求**全部永久挂住**（实测 8s 后 12 个请求仍未结束），`/emergency` 因此永远到不了 `networkidle`（`check-page-load`、`check-hydration` 双双超时）。
   **修法**：`generateStaticParams` 返回未编码的原始 `s.slug`；`notFound()` 前对 `decodeURIComponent` 加 try/catch。
   **教训**：`dynamicParams = false` 与"返回编码后的 param"不能同时用；判断路由是否真 404，必须绕过浏览器缓存用原始请求测。

2. **离线的动态预缓存选错了触发点**：为让 12 个"没访问过的场景"也能离线，曾在根 layout 的 `ServiceWorkerRegistrar` 里 postMessage 让 SW 预缓存全部场景 → 该组件在**每次页面加载**都触发 12 个页面抓取。虽然总大小只有约 226KB（场景页 18.8K 字符/页），但会拖住首次访问的 network-idle。
   **修法**：回退到"install 预缓存核心页 + 场景页 network-first 运行时缓存（访问过即可离线）"，正确做法应是把 12 个 URL 写进 `sw.js` 的 `PRECACHE_URLS`（install 只发生一次）。

### 8.2 P0 · 检索核心 bug（影响回答质量的根本问题）

`search-index.ts` 旧实现把**整句当作一个短语**做 `includes`：

```
问「心脏骤停怎么办?」 → wholes = ["心脏骤停怎么办"]  ← 整句永不可能作为连续子串命中
                       → 分句通道贡献恒为 0
                       → 实际只剩"按字重合比例"打分
                       → 高频字（的/了/是/有/人）压过罕见词
实测：正确条目 13-01（心肺复苏）排行第 4，被「亲人刚走的那几天…」（含 心/人/的）盖过
      问「吸烟有什么危害?」→ 正确条目 02-01「戒烟，越早越好」排行第 24
```

**修法**：重写为 **n-gram（2~4 元滑窗）+ IDF 加权**（罕见词权重自动变高，高频词自动趋近 0，不需要维护停用词表），并按 标题 > 说人话 > 收益 分级计分。

**复测（新增 `check-ask-quality` 断言）**：8 个真实问题 top-N 全部命中正确条目，13-01 变第 1、08-02「发现被骗打 110」进入前三。

### 8.4 新增能力

**A. 回答引用校验（把"不编造"从提示词承诺变成服务端保证）**
页面承诺「所有回答只引用原书 · 不编造」，但此前只靠系统提示词自律。新增 `src/lib/verify-answer.ts`：抓出正文里的 `NN-NN` 编号，凡不在**模型实际看到的条目**内即判定为编造 → 丢弃这段 AI 回答、降级为纯检索，并回传 `fallbackReason: 'uncited'`（界面明示「AI 回答引用了原书没有的条目, 已改为纯检索结果」）。
> 关键细节：不能用 `\b` 边界 —— 它会把日期 `2026-09-20` 里的 `09-20` 当成条目编号，导致含日期的**正常回答**被误判丢弃。已改为前后否定环视 `(?<![\d-])(\d{2})-(\d{2})(?![\d-])`。

**B. 「急方」分步卡接入问答（安全相关的功能缺口）**
本站把原书第 13 节整理成了 12 张分步急救卡（离线可用），但 /ask 此前只回条目、不引导到卡片 —— 问「噎住了怎么办」看不到那张 4 步卡。新增 `src/lib/emergency-match.ts`（场景名 + 口语别名匹配），命中时在回答上方给出：4 步要点 + 「打开急救卡（可离线）」，并明确标注**「本站据原书急救章节整理 · 离线可用 · 非原书条目」**，与原书引用区分开。
实测：心脏骤停／噎住／一氧化碳／触电 均正确命中且各 4 步；低钠盐／租房押金／孩子发烧 均不误命中。

### 8.7 追加修复：承诺「不可信的地方会标原书未覆盖」此前并未兑现

页面标语写「不可信的地方会标『原书未覆盖』」，但实测**只有 0 命中时**才会标；只要命中 ≥1 条，无论多不相关都会以「依原书检索, 相关条目如下:」的口吻列 5 条：

```
【推荐一部好看的电影】→ 01-17 女性 40 岁起做乳腺癌筛查…      （无任何提示）
【怎么养一只猫?】      → 05-19 别把钱押在一只股票…            （无任何提示）
【量子力学是什么?】    → 10-07 先看登记数据再听长辈…          （无任何提示）
```

**为什么不能直接加"分数阈值"**：先实测了 8 个真问题 + 5 个离题问题的 topScore ——
真问题最低 49.0（被骗了钱），离题却有 68.2（股票怎么选），**分离度只有 0.72×，阈值根本切不开**。

**真正的根因**：IDF 只能识别"常见=不重要"，但**在本库里罕见的废话**照样被当成高信息量词项：
- 「量子力学是什么?」45 分全部来自词项 **「是什么」(df=9)**
- 「怎么养一只猫?」31 分全部来自 **「一只」(df=9)**

**修法（两步）**：
1. 加**功能性短语黑名单**（是什么/怎么/多少/一只/能不能/推荐… 70 余条）—— 剔除后：猫 **0.00**、量子力学 **0.00**、写诗 15.0，而真问题全部保持不变（安全带 292.8 / 被骗 49.0）。
2. 此时才可设**相关性下限 `MIN_RELEVANT_SCORE = 25`**（实测校准，注释里写明了全部 13 个样本分值与"语料变化后必须重跑校准"的约束）；低于阈值时：正文首行改为「原书未直接覆盖此问题。以下是按字面检索到的相近条目, 未必切题, 请自行判断:」，界面在答案上方加朱砂提示条。

**复测**：猫/量子力学 → 0 引用 + 标注未覆盖 ✅；写诗 → 标注"字面相近" ✅；心脏骤停/被骗/低钠盐 → **不误标** ✅（`audit-ask-offtopic` 2/2、`audit-score-calibration` 1/1 已固化为回归守卫）。

### 8.8 AI 上游接入（中转站，2026-10-16 配置并实测）

**平台分析**（`api.example-relay.com`）：

- **密钥泄漏面已核验**：`.next/static`（客户端产物）搜 `sk-`/域名 **0 命中**；git 跟踪文件 **0 命中**；工作区无 `.env.local` 以外的明文副本；服务端产物里也不含域名（运行时读环境变量）。

**新增测试**：`check-ai-path`（真实调用，断言 `model=ai`、无降级、**正文引用编号 ⊆ 检索结果**、急救题必帶急方卡、带免责声明、不外泄推理过程）。
为省 token，`check-ask-quality` 与 `audit-score-calibration` 已改为**进程内直接调用 `searchEntries`**（毫秒级、零 token），检索质量与阈值校准不再依赖 HTTP。

**遗留风险（因为 AI 一旦开启就是要花钱的）**：
1. **限流可被伪造头绕过**（P0-E）→ 开启 AI 后这是**直接的资金风险**，生产环境务必在边缘做持久化限流。
2. **部署时必须在托管平台单独配置这三个环境变量**（`.env.local` 不会随部署上传）；未配置则自动回到纯检索模式，站点仍可用。
3. 该 token 已在对话中出现，建议按需轮换；仓库与客户端产物已确认不含它。

### 8.9 开源配套：别人 clone 下来怎么配 key（BYOK 设计）

**问题**：密钥必须留在 `.env.local`（不能提交），那 clone 项目的人怎么启用 AI？原来页面**没有任何设置入口**，只能去翻代码/文档。

**设计（三层，各管一件事）**：

| 层 | 谁配 | 配什么 | 为什么这样切 |
|---|---|---|---|
| 服务端 env | 部署者 | `ASK_API_BASE` | 决定"请求发往哪里" —— 属部署决策 |
| **BYOK** | 访问者 | 自己的 key（浏览器 localStorage）| 决定"花谁的钱" —— 可放进页面设置 |
| 不配 | — | 纯检索模式 | 功能完整，clone 即可跑，最小自建成本 0 |

**关键安全边界：页面只接受 key，绝不接受用户填 base URL。**
否则 `/api/ask` 会变成"任意地址的代理"—— 攻击者可以让本站服务器去请求内网服务或云元数据地址（SSRF）。请求发往哪里，只能由部署者用 `ASK_API_BASE` 决定。

**实现要点**：
- 新增 `GET /api/ask`（公开配置）：返回 `{ ai: { baseConfigured, serverKey, byok, models[], defaultModel } }`，供页面显示状态与模型下拉；**不含任何密钥内容**。
- key 经 **`x-ask-key` 请求头**传递（不进 URL、不进 body、不进日志）；服务端做形状校验（可打印 ASCII、无空白、8–200 字符），非法即忽略、回落到服务端 key。
- 模型经 `x-ask-model` 传递，但**必须在服务端白名单 `ASK_MODELS` 内**，否则忽略。
- 优先级：访问者 key > 部署者 env key（自带 key 时花访问者自己的额度）。
- key 存 `localStorage`（`src/lib/ask-settings.ts`，隐私模式写失败静默降级）；页面支持保存/清除，并明示"清除后即从本机删除"。
- 上游失败且用户填了 key 时，界面额外提示"请检查你填的 key 是否有效或额度不足"。

**文档**：新增 `.env.example`（逐项注释，含"推理模型要给足 max_tokens""公开部署必须做边缘限流"两条坑）＋ README「启用 AI 问答（可选，不配也能用）」小节，给出方式一（部署者配 env）与方式二（访问者在页面填 key）两条路径。

**实测（`check-byok` 6/6 全过）**：

| 用例 | 结果 |
|---|---|
| 公开配置端点 | 返回 `baseConfigured/serverKey/byok/models`，且**不含任何 `sk-` 形态字符串** |
| 假 key `sk-definitely-not-a-real-key-000` | `model=search-only` + **`fallbackReason=upstream`**（而非 `no-key`）→ 证明真的用了访问者的 key；响应不回显 key |
| 非法 key（`abc` / 含空格 / 300 字符）| 被忽略 → 回落到服务端 key → 正常出 AI 回答 |
| 伪造 `x-ask-base: http://169.254.169.254/...` | **被忽略** → 仍走服务端配置地址 → 正常出 AI 回答（**SSRF 边界成立**）|
| 伪造 `x-ask-model: 非白名单模型` | 被忽略 → 用默认模型 → 正常 |
| 页面入口 | 入口显示「⚙ AI 设置 · 本站已启用」；key 存进 localStorage；**实测请求 URL 与 body 均不含 key，只有 `x-ask-key` 头带着它**；清除后 localStorage 为 null |

> 未能覆盖的一点（诚实标注）：非 ASCII 的 key **无法作为 HTTP 头发送**（浏览器与 undici 都直接抛 `Invalid character in header content`），所以那条分支在 HTTP 层进不来；服务端仍保留该检查作为纵深防御，防的是 curl / python-requests 之类更宽松的客户端。

### 8.10 「自动展卷」不明显 → 挖出一个**全站按钮都没有边框**的根因

**起因**：用户反馈长卷右下角的「自动展卷」按钮不显眼，读者发现不了。

**先量现状**（不靠观感）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 尺寸 | 78×20px（低于 24×24 无障碍下限）| **96×36px** |
| 字号 | 12px（继承 `text-xs`）| **14px** |
| 颜色 | 淡墨 `#6B5D4A`（像灰字，不是控件）| **朱砂深 `#8B3A3A`** |
| 文字对比度 | 4.69:1，且是"装饰性文字"的观感 | **5.58:1**（AA 达标）|
| 位置 | 混在下方一行灰色小字末尾（`ml-auto`）| **与刻度尺并排自成一组控件** |
| 状态语义 | 无 | **`aria-pressed`** + 运行中朱砂反白填充 |

**然后挖到更严重的根因**：修完顺手量了边框，发现 `border` 工具类**完全没生效**（computed `border-width: 0px`），于是全站所有 `<button class="border border-*">` 外框按钮**都没有边框**，看起来像纯文字 —— 这正是"按钮不明显"的普遍原因。

**根因链**（实测定位，非推测）：
1. `globals.css` 的按钮重置写了 `border: none`；
2. 浏览器把它展开成 `border-style: none`（并附带 `border-width: medium`）；
3. Tailwind 的 `border` 工具类只设 `width` 与 `color`，**不设 `style`**；preflight 的 `*{border-style: solid}` 被元素选择器 `button` 压过；
4. 按 CSS 规则"**style 为 none 时 computed width 归 0**" → 宽度 1px 被算成 0。
   （定位手法：在页面里注入一个干净的 `<button class="border">` 实测 0px，再遍历 CSSOM 列出所有命中规则，看到 `button { border-width: medium; border-style: none; ... }`。）

**修法**：把重置改成只归零宽度、保留 solid —— 默认同样无边框，但工具类能生效：
```css
button { border-width: 0; border-style: solid; /* 不写 border: none */ }
```
**影响面**：全站外框按钮一次性恢复边框（首页/矩阵/海报/我的/问答/AI 设置面板/长卷刻度区…），这也是本次"按钮不明显"问题的真正解药。

**新增回归**：`audit-autoscroll-button` —— 断言按钮高度 ≥32、对比度 ≥4.5、与刻度尺同排、`aria-pressed` 正确、运行态背景确实改变；桌面(1280) 与手机(390) 各测一遍并出图（`out-autoscroll-1280.png` / `out-autoscroll-390.png` / 运行态两张）。

> 顺带纠正一个我自己的误判：过程中我用 `Get-Content`（PS 5.1 默认按 ANSI 解码）看 `globals.css`，输出里中文注释成了乱码，我一度以为文件被损坏；改用 .NET UTF-8 读取复核后确认**文件一直是好的**，是命令的编码问题。教训：读文件一律用 UTF-8 显式解码。

### 8.11 「人生阶段 → 章节」映射核实：内容正确，但覆盖与口径有两处真问题

用户反馈「人生阶段里对应的章节内容貌似映射不准确」。核实方法：把每个阶段**描述里宣称的主题**拿去原书 765 条正文里检索，看它们是否真的落在该阶段映射的章节内；并逐章抽样核对章节内容。

**结论一：内容级映射是准确的**（未改动）。抽样证据：
- 第 20 章「刚出生的孩子怎么带」→ 20-01 仰着睡/硬平面/同房不同床、20-02 乙肝疫苗、20-04 纯母乳与辅食 ✓ 只归「婴幼儿」正确

- 第 30 章「上学以后的孩子」→ 30-03 欺凌当天报到学校、30-04 每天户外 2 小时防近视、30-05 屏幕时间 ✓ 6-15 岁

**结论二：覆盖有缺口（真问题）** —— 34 章里 **10 章不属于任何阶段**，从「人生阶段」入口永远进不去：

其中 **13 紧急情况 / 24 看病 / 29 重大打击 / 3 精力 / 4 时间 / 6 反面清单** 显然全年龄通用。

**修法（三处一起，让区别"第一眼可见"）**：

3. **阶段页头部**：直接写出「本阶段专属 第 20 章 刚出生的孩子怎么带」+ **「只看专属」**按钮（281 条 → 17 条，只留该阶段专属章节，勾选数变 1）。

**回归**（`check-stages-v2` 扩到 6 条）：
- 6 张卡片文案互不相同、且含各自专属章节名
- 每个阶段侧栏第一组必须是「本阶段专属」、专属标签数 = `own.length`、通用标签数 = 9
- 阶段页头部必须出现该阶段首个专属章节的标题（不用翻侧栏就能看到）
